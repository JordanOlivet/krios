# Progress — 2026-11-22 (release preparation, krios_core extracted, ADR-028)

The user wants a first public version so the project can be found and
added to modpacks: published as "release" on CurseForge and Modrinth,
the 0.x version carrying the alpha state. The session audited what stood
in the way, set up the release pipeline, and extracted `krios_core`
before any world exists outside the dev runs.

## Release audit

Content was consistent (every block and item had its blockstate, model,
texture, loot table, EN/FR names and recipe; no debug leftovers). What
was missing was packaging:

- `fabric.mod.json` still carried the template's links and a
  `suggests: another-mod` block; `neoforge.mods.toml` had no issue tracker
  or display URL; `pack.mcmeta` said `pack_format: 8`. Fixed (d39628b).
- No release pipeline, no tag, no store pages, and the jars had only ever
  run in the dev environment.

## Release pipeline

- `ci-workflows` PR #11 (open): `publish-mod.yml` gains `tag-prefix` and
  `changelog-paths`, so a monorepo can tag `industry/v0.1.0` (ADR-009)
  and keep each mod's changelog to its own commits. Farfield's caller is
  unaffected.
- `.github/workflows/industry-release.yml` and `core-release.yml`: tags
  `industry/v*` and `core/v*`, both loader jars to Modrinth, CurseForge
  and a GitHub Release. A tag without a pre-release label publishes as
  "release". They call `publish-mod.yml@v1`: they work once PR #11 is
  merged and `v1` has moved. Variables per mod (`INDUSTRY_MODRINTH_ID`,
  `INDUSTRY_CURSEFORGE_ID`, `CORE_MODRINTH_ID`, `CORE_CURSEFORGE_ID`),
  shared secrets `MODRINTH_TOKEN` and `CURSEFORGE_TOKEN`. None is set yet.

## krios_core extraction (ADR-028, user call)

ADR-018 planned it for the start of krios_storage and accepted the
namespace change of the KOIOS content. With a public release coming,
that change would have broken players' worlds, so it was done now.

- `mods/core` is a second standalone build. It owns the KOIOS core, the
  casing, the conduit, the ores and materials, the Calibrator, the compute
  chip, their data and assets, the network engine, the scheduler, the
  config and commands, the shared platform services and the terminal
  chrome. Industry keeps machines, modules, kits, the Engram and its
  balance (`IndustryBalance`).
- Industry includes core as a composite build; its jars declare
  `krios_core` as required and do not embed it.
- Two registries let a mod feed core's screens: `CodexEntries` and
  `KoiosUnlocks`.
- Commands: `/krios_core config`, `/krios_core koios`, `/koios`. The
  world config file is `serverconfig/krios_core-server.properties`.
  `/krios_industry` has no command until ADR-019's overrides are built.
- `mods/industry/tools/gen_textures.py` and `gen_ore_glow.py` now write
  core-owned textures into `mods/core`. Neither was run (no texture was
  regenerated; the moved textures are the same files, `git mv`).

## Validated

- Full `build` (javadoc included) green for both mods; Industry's jars
  contain no core class.
- Industry's NeoForge and Fabric dev servers boot with both mods and no
  error in the log; over RCON: core and industry blocks placed, their
  block entities saved under the new ids, both loot tables drop, and
  `/krios_core config`, `/krios_core koios info` and `/koios info`
  answer.
- Asset cross-check for both mods: nothing missing, no dangling
  reference, EN and FR keys aligned (core 124, industry 238).

Not validated: no client was started. Screens, the Codex order, the
unlock list on the core terminal, the creative tabs, the emissive ores
and the Calibrator overlays moved or were rewired and need a play test.
Core was not run alone, only alongside Industry.
